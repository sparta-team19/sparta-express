## 👨‍👩‍👧‍👦팀원 소개
## 팀원 소개

| 이름   | 역할            | 
|--------|---------------|
| 김우진 | 사용자 도메인 개발, AI 연동 기능 개발, Slack 메시지 개발 | 
| 김성용 | 허브 도메인 개발 | 
| 이창연 | 주문, 상품, 업체 도메인 개발 |

## ✨프로젝트 핵심 목표
'물류 관리 및 배송 시스템'을 개발하며 MSA의 복잡성을 이해하고, 구축할 수 있는 역량을 높힘

- MSA 애플리케이션 구성
  - 유레카 서버로 모든 애플리케이션 관리
  - 게이트웨이로 모든 인입을 관리
  - 게이트웨이에서 인증 및 권한 확인
- 허브간 이동정보 관리
  - P2P 모델을 사용하여 허브 간 이동정보 경로 모델링
- 생성형 AI API 활용 배송 예상 시간 생성 및 알림 처리
  - Gemini API 활용하여 상품 및 주문, 배송 내용을 통해 최종 발송 시한 생성
  - Slack API 활용하여 최종 발생 시한 메시지 알림

 ## ⛏️기술스택
 **Back-end**

- **Java 17 / SpringBoot 3.4.0 / Spring Security / Spring Cloud / JPA**

**DB**

- **PostgreSQL, Redis**

  <summary><b>2. User Service</b></summary>

<details>
  <summary>3. Company - Product Service</summary>
  <!-- 내용 -->
  - 역할: **업체와 상품 정보 관리**
  - 기능:
    - 업체 등록, 수정, 조회 기능
    - 상품 생성, 수정, 삭제 및 조회
    - 업체와 상품 간의 관계 모델링
</details>

<details>
  <summary><b>4. Order Shipment Service</b></summary>
  <!-- 내용 -->
  - 역할: **주문 및 배송, 배송 경로 관리**
  - 기능:
    - **주문 생성 프로세스**
        - **FeignClient**를 통해 다른 **service**와 동기 방식으로 통신
        - **플래그 기반 보상 트랜잭션**
            - 재고 감소 후 에러 발생 시 재고를 복구하여 데이터 일관성을 유지
        - **오류 발생**에 대비해 **Fallback 메커니즘**을 구현
        - **Circuit Breaker** 적용하여 장애 발생 시 시스템 과부하를 최소화
</details>

<details>
  <summary>5. AI-Slack Service</summary>
  <!-- 내용 -->

  - 기능:
    - **최종 발송 시한 생성 프로세스**
        - AI(Gemini) API 를 사용하여 최종 발송 시한을 생성
        - AI 요청 및 응답 생성, 삭제, 조회, 검색
    - **메시지 발송 프로세스**
        - Slack으로 수신자에게 Bot을 사용하여 메시지 전송
        - Slack 메시지 생성, 수정, 삭제 (Slack API 사용)
        - Slack 메시지 조회, 검색
</details>

## ❓고려사항
<details>
  <summary>허브간 이동경로 모델링</summary>
  <!-- 내용 -->
  - **Hub 2 Hub 방식
  B2B** 비지니스에서 Hub 2 Hub 방식을 채택하게 되면, **대량 운송을 통한 비용 최적화** 등이 가능
- **다익스트라 알고리즘
  물류 센터**는 기본적으로 **오랜 시간과 큰 비용을 들여 구축/증축**하게 되며, **이를 위한** **계획 수립이 필요.**
  그러기 위해선, 특정 물류 센터 **구축/증축에 어느 정도 규모가 필요한지 파악하기 용이한 시스템이어야함.**
  이와 같은 조건을 충족시키기 위해, 매번 이동 경로 정보가 바뀌는 방식보다 **미리 정해진 이동 경로간 정보를 통해 출발 
  허브에서 도착 허브간의 허브 경로가 결정되는 것이 적절.** 특정 허브/허브간 경로가 사용 불가능 할때는 실시간성으로 경로를 찾아내기 보단, 대체 허브/허브간 경로를 지정하여 최적 경로를 판달할 수 있는 방식이 적절.
  이렇게 **이동 경로의 시간/거리가 일정한 상황에서 최적 이동 경로**를 산출해내기엔 **다익스트라가** 적절하기에 채택
</details>

<details>
  <summary><b>허브 경로 도메인 ConcurrentMap Spring 기본 캐싱</b></summary>
  <!-- 내용 -->
  - **작은 데이터 규모
  물류센터의 구축엔 매우 큰 비용과 시간이 소요**되므로, 꽤나 오랜시간 동안 **물류센터 허브/허브간 경로 데이터가 변하지 않을 가능성**이 큼. 따라서, 허브, 허브간 경로, 출발 허브 - 도착 허브간의 경로 등의 데이터 규모가 작은 규모로 오랜시간 유지될 가능성이 큼. **허브 17개, 허브간 경로 24개** 규모에서 나올 수 있는 출발/도착 허브경로의 데이터 규모는 매우 작음.
  - **대부분 서비스 레이어 캐싱에서 끝나는 API
  허브/허브간 경로 정보가 미리 정해진 채로 오랫동안 유지**되기에, 출발 - 도착 허브의 이동 경로 역시 오랜시간 같은 상태로 유지. 이는 이 도메인에서 **요청 받는 대부분의 조회 데이터(허브, 허브간 경로, 출발 - 도착허브간 이동경로)가 대부분 캐시에서 조회**되고 끝난다는 것을 의미. 따라서, 대부분의 경우 **수평확장이 필요할 가능성이 거의 없다고** 해석.
  - **결론**
  캐시 데이터 **규모가 작고, 수평확장을 고려할 필요가 적기**에, **추가로 인스턴스와 구현 작업이 필요하지 않은** spring 기본 캐싱 기능을 활용하는 것이 적절. 네트워크 통신 문제로 인한 에러/경미한 속도 저하 등을 고려하지 않아도 되는것 역시 이 방식의 장점.
추후 레디스로 캐시를 바꿀 일이 있어도,  스프링의 캐시기능은 aop 방식을 통해 작동하므로 수정이 쉽기에 일단은 기본 캐시만 써도 무관하다고 판단.
</details>
